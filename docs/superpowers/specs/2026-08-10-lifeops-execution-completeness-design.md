# LifeOps Web 执行完整性与跨会话接班设计

**状态：** 执行保障层已完成并进入 `implementation-active`；2026-08-14 视觉实现质量增量与 2026-08-21 ADR-026 记录合同增量已批准  
**日期：** 2026-08-10；视觉实施质量增量 2026-08-14  
**上位决策：** ADR-016、ADR-017、ADR-018、ADR-019、ADR-020、ADR-021、ADR-022  
**产品权威：** 最终重设计规格、生活专区设计、镜像交付边界、主计划与 P1–P6  
**目标：** 把“完整实现每个页面、功能、状态和交付细节”从协作承诺变成可检查、不可跳步、可跨会话恢复的执行合同

## 1. 问题定义

LifeOps Web 已有完整产品规格、44 个主需求和六个有序工作包，但仅靠人工阅读仍存在四类风险：

1. 一个主需求包含多个页面、状态、断点和数据事务，主需求行通过并不自动证明全部细节通过。
2. 计划步骤可以被勾选，却没有新鲜测试、真实浏览器检查或发布证据。
3. 新对话可能只看到宏观目标，没有读到唯一活动任务、禁止恢复的设计和精确下一步。
4. 测试、截图或镜像/registry 输出可能来自旧源码、跳过套件、模拟数据或错误制品，却被误认为当前证据。

本设计不承诺模型永不犯错。它承诺：遗漏、陈旧证据、跳步和不真实完成声明必须被检测，并阻止任务、阶段或项目关闭。

## 2. 范围与非目标

### 2.1 本设计负责

- 把 44 个主需求拆成可独立判定的原子验收条目。
- 建立规格条款、原子条目、计划任务、源码、测试、视觉证据、镜像和 UHub 发布证据之间的双向追踪。
- 为启动、任务关闭、阶段关闭、交接和项目关闭提供机器校验。
- 规定每个页面、跨页面流程、数据事务、响应式状态和连续动效的人工验收方式。
- 规定暂停、新对话、上下文压缩和执行者切换后的只读接班流程。
- 保持现有 P1 → P6、TDD、真实 MySQL、真实浏览器、精确 digest 镜像和 UHub 门禁不被弱化。

### 2.2 本设计不负责

- 不调整任何已确认的产品功能、信息架构、视觉语言或发布主线。
- 不增加第 45 个产品主需求；原子条目是 44 个主需求的子条款，不是新范围。
- 不用自动校验器替代视觉判断、用户设计确认、镜像 smoke 或真实 registry 验证。
- 不把旧测试、旧截图、模拟平台数据、本地 Helm 渲染或只在本地存在的镜像升级为 UHub 证据。
- 本设计阶段不初始化 Git、不创建外部仓库、不推送镜像；后续发布只有在得到相应授权和环境条件时执行，且不访问或变更用户集群。

## 3. 五层执行真相

### 3.1 产品权威层

权威顺序继续服从项目 `AGENTS.md`。最终重设计规格、生活专区设计、执行完整性设计、镜像交付边界设计和主计划这五份文件，以执行控制中的 SHA-256 为批准快照。任何哈希不一致都先进入变更控制，不能在未知漂移上继续实施。

### 3.2 主需求层

`docs/traceability/requirements.md` 继续保存 44 个主需求的聚合状态。主需求状态必须由其原子条目和证据推导，不能只靠手工把一行改为 `verified`。

### 3.3 原子条款层

新增机器可读的 `docs/traceability/acceptance-matrix.json`。每个原子条目只表达一个可以明确判定通过或失败的合同，例如：

- `LIFE-02.CALENDAR.STATE.04`：过去且存在未完成计划的日期必须显示未完成状态，且不能与“已有计划”完全同形同色。
- `LIFE-11.INVENTORY.TXN.03`：相同用户、操作和幂等键的完成请求重试不得产生第二条库存扣减流水。
- `AUTH-01.LOGIN.MOTION.05`：关闭登录层必须从当前轨道相位反向恢复，不能重置动画。

原子条目禁止把可独立失败的多个行为塞进一句“全部正常”。

### 3.4 证据层

新增 `docs/traceability/evidence-manifest.json`，只登记脱敏证据的元数据、命令、退出码、源码检查点、产物路径和哈希。测试输出、截图、视频、JSON 摘要、镜像 smoke 和 registry 摘要保存到 `outputs/evidence/`；凭据、Cookie、私有正文、kubeconfig 和原始敏感日志永不进入证据目录。

### 3.5 当前状态层

`docs/superpowers/plans/2026-08-09-execution-control.md` 继续是唯一活动任务状态机。它记录活动计划、任务、步骤、下一原子动作、权威哈希和当前门禁结果；聊天记录不是执行状态源。

## 4. 规格条款清点

仅拆分 44 个主需求仍可能漏掉规格中的细节，因此增加 `docs/traceability/source-clauses.json`：

1. 初始清点必须同时覆盖五份 SHA-256 锁定的权威文件和全部六份有序工作包：最终重设计、生活专区、执行完整性、镜像交付边界、主计划，以及 P1 至 P6。不能只清点当前工作包后就让 `startup` 通过。`AGENTS.md`、execution-control、CURRENT 和最新 session 的动态状态字段由状态一致性校验单独负责，避免把交接值误当成静态产品条款。
2. 从上述十一份文件中提取标题、规范性段落、列表项和表格行；保存固定来源键、标题路径和同级序号，使文本内容变化时 ID 保持可追踪、文本哈希失效。
3. 每条保存来源文件、章节、规范文本摘要和文本 SHA-256。
4. 每条必须被分类为：
   - `mapped`：映射到一个或多个原子条目；
   - `context-only`：只是背景或解释，必须填写非规范理由；
   - `superseded`：只在有明确 ADR/用户修订证据时使用，并记录替代来源。
5. 未分类条款、无原子条目的规范条款、无来源条款的原子条目都会使校验失败。
6. 规格变化导致文本哈希变化时，旧映射失效；必须重新审查，而不是静默沿用。

自动提取只能生成候选，最终规范性分类由主执行者逐条复核。这样既避免脚本假装理解语义，也避免人工只阅读熟悉部分。

## 5. 原子验收模型

### 5.1 稳定 ID

格式为：

`<父需求>.<表面或领域>.<维度>.<两位序号>`

允许维度：

| 维度 | 含义 |
|---|---|
| `LAYOUT` | 页面区域、层级、首屏利用和空间关系 |
| `FUNC` | 用户可以完成的单一操作 |
| `DATA` | 字段、来源、关联、隔离和历史真相 |
| `CALC` | 确定性换算、聚合、预算或预测公式 |
| `TXN` | 事务、幂等、反向流水和并发保护 |
| `STATE` | 加载、空、保存、错误、冲突、离线、权限、断开 |
| `NAV` | 进入、返回、深链、浏览器历史和状态恢复 |
| `RESP` | 宽屏、笔记本、平板和手机重排 |
| `A11Y` | 键盘、焦点、语义、对比、触控和替代操作 |
| `MOTION` | 进入、退出、反向、打断和减少动态 |
| `SEC` | 隐私、鉴权、净化、凭据和最小权限 |
| `OPS` | 可观测性、部署、降级和环境事实 |

### 5.2 必填字段

每个原子条目必须包含：

- `id`：稳定且唯一。
- `parentRequirementId`：44 个主需求之一。
- `title` 和单一、可判定的 `contract`。
- `sourceClauseIds`：一个或多个来源条款。
- `surfaces`：路由、组件、API、数据表或交付边界。
- `plannedTasks`：负责实施的 P/T 任务。
- `requiredEvidence`：需要哪些证据类别。
- `finalBoundary`：`local`、`image`、`registry` 或适用组合。
- `notApplicable`：仅在确实不适用时存在，并包含具体理由和批准来源。

状态不由矩阵手写。校验器根据证据清单计算 `pending`、`partial`、`verified-local`、`verified-image`、`verified-registry` 或 `invalidated`。

### 5.3 原子性判定

一个条目必须满足：

- 单个测试、单次人工检查、单个镜像探针或 registry 查询能给出明确结论。
- 条目失败时可以指出一个具体缺陷，而不是“页面不够好”。
- 桌面和移动表现能独立失败时必须拆分。
- 正向与反向事务能独立失败时必须拆分。
- 正常态与错误/冲突/离线态必须拆分。
- 数据计算与视觉呈现必须拆分。

## 7. 每页最低维度合同

每个可视页面必须在矩阵中明确以下维度；不适用时必须写理由：

1. 页面主角、上下文和主操作。
2. `1440×900` 首屏主任务及始终可达的返回/关闭/保存。
3. 正常、初载、局部刷新、空、保存中、已保存、错误、冲突、离线、权限、删除/撤销和未连接状态。
4. 桌面 `1440×900`、笔记本 `1024×768`、平板 `768×1024`、手机 `390×844`。
5. 键盘顺序、焦点进入/恢复、`Esc` 层级、44px 触控和非颜色状态提示。
6. 进入、退出、返回、快速打断、滚动/筛选/选择恢复和 `prefers-reduced-motion`。
7. 页面涉及的 API、数据表、计算和写事务。
8. 单元/API/MySQL/E2E/视觉/镜像/registry 中实际适用的证据。

页面缺少其中任何适用维度时，校验器必须报告具体页面和维度，不允许用一个全局 `STATE-01` 或 `LIFE-23` 证据替代所有页面。

## 8. 证据合同

### 8.1 证据类型

- `unit`：确定性函数和组件行为。
- `api`：Fastify 路由、鉴权、错误和版本合同。
- `mysql`：真实 MySQL 事务、约束、并发、恢复和持久化。
- `e2e-local`：本地真实 Web/API 浏览器流程。
- `e2e-remote`：经真实 Web/API 容器入口、连接真实 MySQL 的远程流程。
- `visual`：指定断点截图或视频以及人工检查结果。
- `a11y`：自动扫描和键盘人工流程。
- `build`：类型检查、生产构建或 Helm。
- `security`：CSRF、XSS、SSRF、隔离、RBAC、Secret 和镜像检查。
- `image`：对精确 Web/API digest 的非 root、健康、深链、API、MySQL 和优雅退出 smoke。
- `registry`：UHub repository/digest inspect、SBOM/provenance、production values 和 release manifest 一致性。
- `delivery-package`：Helm/GitOps/Argo 示例、部署后 smoke、备份恢复与回滚手册的静态、渲染和安全检查。
- `manual-review`：自动化不能判断的层次、空间、审美和动效连续性。

### 8.2 新鲜度

每条证据必须记录：

- UTC/本地执行时间。
- 完整命令和退出码。
- 关联原子 ID。
- 当前源码检查点。
- 测试数量或明确的执行摘要。
- 产物路径和 SHA-256。
- 是否存在跳过；要求的套件出现跳过即不算通过。
- 人工检查者和结论（仅视觉/手动证据）。

源码检查点变化后，受影响文件映射到的证据标记为 `invalidated`。旧证据保留审计，但不能继续关闭当前条目。

正式 Git 仓库存在时，源码检查点使用完整 Git commit，并要求被纳入检查点的路径没有未提交修改。正式仓库尚不存在时，必须生成可机器比较的 `uncommitted-local-checkpoint`：

- 对配置允许列表中的实现、测试、迁移、依赖锁、Docker、CI、Helm/GitOps 和验证脚本逐文件计算 SHA-256；
- 按规范化相对路径排序，将 `path + sha256` 写入脱敏检查点清单，再对规范化清单计算根 SHA-256；
- 检查点清单记录包含/排除规则，排除 `node_modules`、构建产物、临时 MySQL 数据、浏览器报告、凭据和证据目录自身；
- 每条证据记录它实际依赖的源码路径及当时哈希，校验器据此使受影响证据失效；
- 无 Git 检查点只允许支持实现和本地门禁，正式发布前仍必须解决批准的 Git 仓库与 Git revision 边界。

零散文件哈希、目录时间戳或自然语言“源码未变化”不能替代该根检查点。

### 8.3 视觉证据

视觉记录除了产物还必须保存检查项：

- 是否实际打开产物，而非只生成。
- 是否存在横向溢出、裁切、遮挡、不可达操作或无效空白。
- 是否恢复被禁止的星球、卡片墙、直角纸片或深色私人 NOC。
- 首屏主次层级和空间利用是否符合页面合同。
- 进入、返回、反向和快速打断是否连续。
- 减少动态下是否仍保留状态因果。

自动截图成功不能替代这些人工结论。

## 9. 自动校验器

实施阶段新增：

- `scripts/verify-execution-contract.mjs`
- `scripts/verify-execution-contract.test.mjs`
- `package.json` 命令 `verify:execution`

校验器只使用仓库锁定依赖或 Node 标准库，不能依赖未声明的全局工具。

### 9.1 `startup` 模式

命令：

```powershell
npm.cmd run verify:execution -- --mode startup
```

检查：

- 当前目录能找到项目 `AGENTS.md`，且指令文件低于 24 KiB 内部预算。
- 五份批准权威文件 SHA-256 与执行控制一致。
- 十一份条款来源文件全部在来源注册表中，且文件集合与固定清单一致。
- 44 个主需求唯一、完整且无未知 ID。
- 来源条款全部分类，规范条款全部映射。
- 原子 ID 唯一，父需求、任务、页面和证据类型有效。
- P1–P6 和任务编号连续，只有一个活动任务。
- 执行控制、CURRENT 和最新 session 的状态及下一动作一致。
- 输出活动计划、任务、步骤、状态、阻塞项和唯一下一命令。

`startup` 允许存在未完成需求，但不允许结构漂移。失败时禁止编辑实施源码。

### 9.2 `task-close` 模式

命令包含活动任务：

```powershell
npm.cmd run verify:execution -- --mode task-close --task P1-T1
```

检查：

- 状态机未跳级。
- 先有期望行为失败的红测试，再有实现和绿色证据。
- 任务声明文件与实际变更一致；额外路径有解释。
- 任务映射的原子条目拥有当前需要的证据。
- UI 任务包含四断点、人工打开检查、键盘和减少动态证据。
- 数据任务包含真实 MySQL；要求 MySQL 时跳过即失败。
- 当前任务交接、哈希或 Git 提交真实存在。

### 9.3 `phase-close` 模式

检查当前工作包全部任务完成、回归命令处于同一源码检查点、该阶段负责的原子条目达到预定边界，且下一工作包没有提前实施。

### 9.4 `handoff` 模式

检查 execution-control、计划勾选、需求账本、原子矩阵/证据、CURRENT 和当前 session 已同步，并且只保存一个可直接执行的下一原子动作。

### 9.5 `project-close` 模式

只有以下内容全部存在才通过：

- 44 个主需求的所有原子条目达到最终边界。
- Web/API、MySQL、E2E、视觉、可访问性、安全、构建和 Helm 门禁处于同一最终检查点。
- Web/API 不可变 UHub digest。
- 正式 Git/SHA 发布检查点与 production values revision。
- 对同一源码检查点的 Web/API 精确 digest 镜像 smoke。
- UHub registry inspect、SBOM/provenance 状态与 production values digest 一致。
- Helm/GitOps/Argo 示例、部署后 smoke、备份恢复和回滚文档通过交付包校验。
- 应用运行时已知单点和所有未连接平台能力仍如实记录。

## 10. 单任务执行协议

任何 P/T 任务按以下顺序：

1. 运行 `startup` 并读取完整活动任务。
2. 标记唯一活动任务，不修改其他任务状态。
3. 为本任务原子条目写明确失败测试。
4. 运行并记录行为失败；语法、依赖、连接或路径失败不算红测试。
5. 只实现本任务合同。
6. 运行聚焦测试、任务回归和适用的真实 MySQL。
7. UI 变更在真实浏览器检查四个断点、正反动效、键盘和减少动态。
8. 反向从原子条目审查源码和证据，而不是只从改动文件向前解释。
9. 运行 `task-close`；失败则留在当前状态。
10. 创建真实 Git 提交；没有 Git 时生成包含逐文件 SHA-256 和根摘要的 `uncommitted-local-checkpoint`。
11. 更新交接后才允许进入下一任务。

## 11. 数据闭环审查

每个涉及共享数据的任务除了本页测试，还要声明受影响消费者。校验器读取影响图，要求相应测试或明确未受影响理由。

最低影响图包括：

- 食材/补剂/药品/家庭物品 → 单位、价格、库存、采购和回收站。
- 食材 → 食谱 → 日期计划 → 营养/成本/库存预测 → 今日/分析。
- 配方版本 → 未来计划重算；完成快照保持不变。
- 库存流水 → 余额、批次、缺口、采购建议和分析。
- 完成/撤销 → 快照、正反流水、汇总和预算证据。
- 购买/退货 → 现金、库存、价格历史、采购状态和预算。
- 分类/标签/位置稳定 ID → 所有消费者即时反映重命名和排序。
- 回收站/导入 → 关系保护、恢复、事务回滚和审计。
- 私人来源 → 公开草稿 → 发布版本；公开端不能反查私人原文。

任何“改一处全平台同步”的要求都必须同时有生产代码、领域测试、API/MySQL 测试和至少一个跨页面 E2E。

## 12. 新对话接班协议

新对话必须在当前 LifeOps Web 工作区根目录启动。当前目录还不是 Git 仓库，因此不能依赖 Git 根自动发现；在仓库边界解决前，错误目录是停止条件。

新对话第一步只读执行：

```powershell
npm.cmd run verify:execution -- --mode startup
```

在编辑前必须向用户报告：

- 加载的权威文件。
- 权威哈希是否通过。
- 当前计划、任务、步骤和需求计数。
- 当前阻塞和未验证外部事实。
- 唯一下一原子动作和第一条验证命令。

推荐继续口令保持简短：

`继续 LifeOps Web，严格按 AGENTS.md 和 execution-control 从当前任务继续。`

口令只触发启动协议，不携带事实；事实始终来自工作区和项目 Obsidian 账本。

## 13. 无旧聊天上下文验收演练

执行校验器后必须进行一次真实新任务的只读演练。由于创建用户可见的新任务需要用户明确触发，验收方式为：

1. 用户在同一工作区新开任务并使用推荐继续口令。
2. 新任务不读取旧聊天，只运行启动协议。
3. 它必须准确报告当前状态、哈希、下一动作、禁止设计和外部边界。
4. 它不得修改源码、不得跳到 UI、不得宣称测试、镜像或 UHub 已通过。
5. 报告与 execution-control、CURRENT 和最新 session 逐字段比对。

字段全部一致才标记连续性 `verified`。只复制文件但未演练时只能标记 `restored/planned`。

## 14. 暂停与交接

每次暂停、上下文边界或任务完成前按顺序更新：

1. execution-control。
2. 当前工作包任务状态。
3. 44 行需求账本。
4. 原子矩阵和证据清单。
5. 项目 CURRENT。
6. 当前 S014+ session。

交接必须记录：活动计划/任务/步骤、已经验证和仍未验证的原子 ID、变更路径、Git 提交或文件 SHA-256、完整命令及退出码、视觉产物、未验证外部事实和唯一下一原子动作。若任一项不一致，`handoff` 模式失败，新对话先修复交接而不是继续实现。

## 15. 失败与变更控制

- 校验器失败：停在当前状态，修复控制数据或真实实现，禁止删除门禁来获得绿色结果。
- 计划命令无法运行：记录准确阻塞，不用更弱检查替代。
- 发现规格不可实现或冲突：先保存证据，向用户说明最小选项，获得确认后依次更新 ADR、规格、主计划、工作包、来源条款、原子矩阵和哈希。
- 用户改变设计：从第一个被影响的原子条目和任务重新验证，不继续沿用旧视觉或旧证据。
- 证据泄密：立即停止登记，移除敏感产物并重新生成脱敏证据；不得把清理后的描述冒充原始通过证据。
- 校验器自身缺陷：先为缺陷写失败测试，再修复；不能手工绕过并关闭产品任务。

## 16. 实施顺序

本执行控制增量必须在 P1-T1 前完成：

1. 书面规范获得用户复核。
2. 编写独立实施计划，明确文件、测试、命令和退出门禁。
3. 先测试后实现来源条款清点、原子矩阵、证据清单和校验器。
4. 完成所有规范条款的初始人工分类和原子映射。
5. 运行 `startup` 与 `handoff` 校验。
6. 完成真实新对话只读演练。
7. 将 execution-control 切换为 `implementation-active`，仍从 P1-T1 Step 1 开始。

这个增量不改变 P1–P6 顺序，也不允许先做可见页面。它只增加进入 P1 的前置执行保障。

## 17. 本设计完成定义

本设计本身只有在以下条件全部满足后才可进入 P1：

- 书面规范经用户确认。
- 原子矩阵覆盖 44 个父需求、所有页面、跨页面事务和适用状态维度。
- 所有规范条款已分类且规范条款全部映射。
- 校验器测试覆盖正常、哈希漂移、重复 ID、孤儿条款、状态跳级、陈旧证据、缺少视觉检查、跳过 MySQL、交接不一致和伪造完成声明。
- `startup` 与 `handoff` 在当前工作区通过。
- 新对话只读接班演练通过。
- 当前真实状态仍为 P1-T1 Step 1、0/44，业务代码未提前开始。

在这些条件完成之前，只能报告“执行保障设计/实施中”，不能报告 LifeOps Web 实现已开始或项目已全面完成。

## 18. 2026-08-14 视觉实施质量增量

### 18.1 批准设计与实现证据分离

- ADR-022 和更新后的最终重设计/生活规格代表“设计已批准”，不代表尚未实现页面已经 `visually_verified`。任何 parent 或 atom 不得因为设计文档完成、截图生成、Skill 运行或目标模式 active 而推进产品状态。
- 新设计条款必须进入现有来源条款注册表，并映射到现有或必要新增 atom；不得建立一套脱离 `acceptance-matrix.json` 的平行视觉清单。44 个 parent 继续由最弱适用 atom 汇总，机器状态仍从 0/44 继续。
- 视觉身份、页面结构、状态/数据真相、无障碍、性能/动效是五个独立否决维度。一个维度失败不能由其他维度或总通过数补偿。

### 18.2 黄金切片质量棘轮

- P2 在铺开五个公开详情前，先以公开首页＋登录形成公开黄金切片；P3 在铺开私人/生活页面前，先以稳定私人 shell＋总览＋一个复杂操作页面形成私人黄金切片。黄金切片必须完成相应任务的 TDD、四视口真实浏览器、关键状态、键盘/焦点、normal/reduced/paused 动效、性能 trace 和人工整体观感复核。
- 黄金切片未通过时，后续相邻 UI 任务保持 pending；不得先批量复制通用卡片、临时样式或占位页面后再声称统一美化。黄金切片通过后形成 living baseline，但后续页面仍必须保留领域原生几何，不能复制同一页面骨架。
- 自动测试、axe、像素比较和原子计数只能证明各自边界。主执行者必须打开全部要求截图/页面，并保留“逐项绿色但整页仍模板化、普通或违背品牌”的人工否决权；重大设计偏离仍回到变更控制并请求用户批准。

### 18.3 可复现视觉与动效证据

- 每份视觉证据登记当前允许列表 root SHA-256、构建命令与退出码、浏览器名称/版本、viewport、DPR、缩放、字体加载、昼夜/时间条件、fixture 或 API 场景哈希，以及 normal/reduced/paused 动效状态。无 Git 阶段仍以确定性允许列表根绑定证据，不能使用文件时间戳或零散截图名替代。
- 静态页面至少在 1440×900、1024×768、768×1024、390×844 逐张打开检查，并执行 200% 文本缩放和 320 CSS px 回流压力测试。动态路径必须使用 filmstrip、trace 或视频验证可中断、反向返回、滚动/焦点恢复、暂停和登录无白闪；单帧截图不能关闭连续性 atom。
- 测试 fixture 必须明确标记并绑定场景哈希；生产页面只接受 Fastify/MySQL 或已批准真实只读适配器的数据。fixture、mock adapter 或设计图不得冒充生产连接、平台状态或完整产品证据。

### 18.4 UI 任务关闭附加门禁

适用 UI 任务只有在以下条件全部满足时才能从 `regression_green` 进入 `visually_verified`：

1. 有效行为红测、最小实现、focused green 和任务/计划回归均来自同一源码检查点。
2. 四正式视口、关键状态、键盘、焦点、返回、reduced-motion 和适用性能证据均绑定该检查点。
3. 主执行者逐张打开视觉产物并记录布局、层次、反模式、裁切、文字密度、对象语言和交互连续性结论。
4. 与批准规格和已存在黄金切片并排复核，无米灰直角通用工作台、私人银河、左侧栏＋卡片墙、整轨自转、悬停才有标签、白闪或同节点双动效引擎回归。
5. 证据清单中没有 skip、todo、unknown 必需项、未打开截图、未运行浏览器或无法复现的外部事实。

Skill 和目标模式仅帮助执行以上步骤；它们不新增完成状态，也不能作为 evidence type。
