## State machine

Allowed task states are:

`pending → in_progress → red_verified → implementation_complete → focused_green → regression_green → visually_verified/not_applicable → checkpointed → completed`

Rules:

- Only one task may be `in_progress` or any intermediate active state.
- A state cannot be skipped. `visually_verified` is mandatory for UI tasks; API/data-only tasks record `not_applicable` with the reason.
- `red_verified` records the command, exit code and expected behavioral failure text.
- `focused_green` and `regression_green` require fresh full output from the current source state.
- `checkpointed` requires a real Git commit when an approved repository exists, otherwise SHA-256 values plus `uncommitted-local-checkpoint`.
- A failed or skipped required check moves the task back to the relevant earlier state; it never advances.

## Per-task enforcement checklist

- [ ] Re-read the active task and confirm no critical plan gap.
- [ ] Inspect repository/worktree and overlapping user changes.
- [ ] Mark only this task active in this ledger and the plan.
- [ ] Write the exact named failing test.
- [ ] Run it and capture an expected behavioral failure.
- [ ] Implement only the active task's behavior and states.
- [ ] Run focused tests/type checks.
- [ ] Run the task and plan regression commands required at this point.
- [ ] Inspect required browser breakpoints and motion when UI changed.
- [ ] Compare changed files against the task's declared file list; explain additions before keeping them.
- [ ] Reverse-check the mapped requirement IDs against implementation and evidence.
- [ ] Inspect diff/content independently; never trust a delegated completion statement.
- [ ] Save commit or SHA checkpoint, commands, exit codes and evidence paths.
- [ ] Update project CURRENT and the active implementation session.
- [ ] Advance to the next task only when every applicable item above is evidenced.

The implemented validator enforces structural, state, evidence, handoff and close-mode invariants; the primary executor still performs the checklist review and fresh commands because automation does not replace source inspection or visual judgment.

## Anti-drift checks at every task boundary

1. Search changed UI for forbidden private universe/card-wall/paper-sheet patterns and wheel navigation.
2. Search production paths for sample/mock/fabricated platform data.
3. Check that no required route, state, mobile layout, accessibility path or reverse transition was dropped.
4. Check that plan-specified tests were run rather than replaced by a smaller convenient subset.
5. Check requirement status against `docs/traceability/requirements.md`; implementation without evidence remains open.
6. Check that CURRENT/session describes actual fresh state and does not inherit historical pass counts.
7. For delegated work, inspect every changed file and rerun verification in the primary session.

## Change-control protocol

If implementation reveals that the approved plan is technically impossible or materially wrong:

1. Stop before implementing a divergent alternative.
2. Record the concrete source/runtime evidence and affected requirement IDs.
3. Explain the smallest viable options and their tradeoffs to the user.
4. Obtain explicit confirmation for any material design, scope, data or delivery change.
5. Update ADR/spec/master/current work-package/traceability in that order.
6. Recalculate the authority hashes above and record why they changed.
7. Resume from the first invalidated task, not from whichever screen is easiest.

## Phase and project completion gates

- A task completes only after the state machine reaches `checkpointed` with fresh evidence.
- A plan completes only after every task is complete and its full regression/visual gate passes in the same source state.
- A requirement completes only after the reverse traceability row links current source, tests and required visual/image/registry evidence.
- After the ADR-018 matrix exists, a requirement's rollup cannot exceed the least-complete applicable child atom; a manually edited parent status is invalid.
