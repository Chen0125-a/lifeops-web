# LifeOps 参考网站深度研究

日期：2026-08-09  
状态：研究完成，尚未形成 LifeOps 重设计决策  
范围：[Active Theory 当前版](https://activetheory.net/work)、[Active Theory V4](https://v4.activetheory.net/work)、[BuouUI](https://buouui.com/)

## 研究方法

- 在真实浏览器中观察首屏、入场、静置动画、指针反馈、滚动、作品切换与详情页。
- 读取可见 DOM 与媒体结构，区分真正的页面内容、隐藏的可访问链接层和 Canvas/WebGL 表现层。
- 使用统一桌面视口进行构图对照；浏览器的移动视口覆盖没有可靠生效，因此本报告不声称完成了三站移动端验收。
- DOM 数量只用于判断实现形态，不等同于资源体积或性能结论。

## 核心结论

三个网站看起来差异很大，但高级感来自同一件事：**先建立唯一而稳定的舞台规则，再让字体、内容、转场和交互全部服从这个规则。**

它们没有把“高级”理解为更多渐变、玻璃卡片、发光边框或装饰图标。相反，每个首屏都只有一个明确焦点：Active Theory 当前版是一块悬浮媒体屏，V4 是一组巨型作品标题，BuouUI 是一句明确主张和一组正在工作的组件。其余元素都降低存在感。

LifeOps 当前方向中的星系隐喻是可用的，但仅有圆环、公转和背景渐变还不足以形成世界。下一轮真正需要解决的是：

1. 星系是否是内容和操作发生的真实空间，而不只是首页装饰。
2. 登录前、登录穿越、私人首页和功能详情是否属于同一个连续镜头。
3. 每个功能是否拥有自己的材质、尺度和行为，同时仍服从统一运动语法。
4. 日常操作是否足够直接，不因沉浸感而被迫等待或猜测。

## 一、Active Theory 当前版

### 视觉世界

- 纯黑深场中放置液态、矿物和生物骨骼感的实时 3D 物体，青蓝、紫和少量暖色作为材质反射，不使用普通网页背景。
- 核心作品不是卡片网格，而是场景中的一块厚重悬浮屏幕；相邻作品以侧面物体的形式露出，天然解释“前后还有内容”。
- 颗粒、折射、色散、噪点和低清媒体并非滤镜堆叠，而是统一的“数字遗迹/未来终端”材质系统。
- 顶部导航、左下分类和输入框都退到第二层，主场景始终掌握视觉权重。

### 动效与交互

- 背景始终运行，作品变化不会让世界停止或整页重建。
- 静置几秒也会出现作品更换、视频变化和微小空间漂移，页面具有生命感。
- 指针改变观察角度与层次，但反馈克制，没有弹跳或普遍放大。
- 进入项目详情时先经过明确的加载状态，随后同一媒体屏放大为详情主体；左侧出现摘要与关闭动作，顶部仍保留原导航。
- 详情明确写出 `SCROLL TO CLOSE`，把退出也设计成空间动作，而不是普通返回按钮。

### 信息架构

- 表现层主要由一个 Canvas 与多个视频组成，但页面仍保留项目名称链接、导航和文本输入等语义 DOM。
- 浏览器采样时可见 1 个 Canvas、3 个视频节点和 33 个链接。这说明其结构是“语义层 + 实时场景层”，不是把所有内容都画死在 Canvas 中。
- 项目详情只展示名称、年份/类型、短描述、项目链接与关闭动作，内容极度克制。

### 值得借鉴

- 私人宇宙应持续存在，功能只是观察尺度变化。
- 星球需要成为真实导航对象：选中后能放大、承载内容并可逆返回。
- 加载、进入和退出都应属于同一种空间语言。
- 背景动态应有自治运动，不能只在用户交互时短暂播放。

### 不应照搬

- 长时间加载、重视频与持续 WebGL 对个人日常工具过重。
- 自定义滚动和 Canvas 命中容易削弱键盘、读屏和低性能设备体验。
- 高噪点、故障感和低清视频适合作品展厅，不符合 LifeOps 的宁静、可信与长期阅读需求。

## 二、Active Theory V4

### 视觉世界

- V4 更像一段全屏电影片头：背景视频占满视口，三行超大窄体标题在同一垂直轴上切换。
- 当前项目使用实心白字，前后项目只保留描边，几乎不需要额外卡片、阴影或说明就能建立层级。
- 右侧只有一根纵向进度尺，顶部只有 Work、Lab、About；屏幕上每个元素都有明确职责。
- 每个项目切换时，背景媒体和整体色温一起变化，项目并非换一张图，而是在换一段氛围。

### 入场与详情

- 入场先展示单独的 `100` 标志，再进入作品场景，品牌记忆点很强，但等待时间明显。
- 列表页的标题体系本身就是导航，不另建项目卡片墙。
- 详情页保留同一背景媒体，巨型标题覆盖在画面上，短说明和外链位于中央；关闭按钮成为右侧独立白色几何物。
- 详情不像新页面，更像当前舞台上展开的一层内容。

### 实现信号

- 浏览器采样时可见 1 个 Canvas、32 个视频节点和 26 个链接。大量项目媒体被组织在同一体验里，这解释了它顺畅切换的能力，也意味着明显的内存、网络和移动端成本。

### 值得借鉴

- 用“当前项实心、邻近项描边/低对比”表达空间层级，比大量卡片更有秩序。
- 一个持续背景可以随所选功能改变灯光、色温和节奏，而不必替换整个页面结构。
- 进度尺或轨迹可以同时承担当前位置、数量和导航反馈。
- 字体不仅展示文案，也可以成为场景的主几何体。

### 不应照搬

- V4 的信息密度适合作品展览，不足以直接承载计划、记录和回顾等高频操作。
- 预载大量视频、长入场和全屏自定义导航不适合每天多次打开的私人系统。
- 巨型标题可以用于进入功能的瞬间，不能长期占据编辑和阅读页面。

## 三、BuouUI

### 视觉世界

- 它不是沉浸式作品站，而是高完成度的产品与组件展示站：暖白/纯白底、近黑正文、单一高饱和紫色作为强调。
- 首屏用极大黑体标题、简短说明和两个动作构成左侧主叙事，右侧直接展示头像、评分、日历和网格组件。
- 装饰主要来自细线网格、结构边界、留白和真实组件状态，而不是玻璃、发光与复杂渐变。
- 导航吸顶，滚动后仍保持搜索、分类和登录入口，产品使用路径始终可见。

### 动效与内容编排

- 首屏右侧组件不是静态插画，而是正在工作的产品片段，因此既建立能力感，也避免“AI 生成大图”的空洞。
- 下滚后先出现明确的大标题和分类，再进入组件示例；每一屏都先回答“这里是什么”，再展示细节。
- Bento 示例通过局部模糊、透明度、横向位移和悬停聚焦制造动态，不依赖整页 3D。
- 悬停时只提升当前内容的清晰度和层级；其他元素退后，信息焦点非常明确。

### 实现信号

- 浏览器采样时可见 3 个 Canvas、130 张图片、147 个链接和 149 个按钮，主体仍是标准 DOM 页面。
- 它证明丰富感不等于把所有内容塞进 WebGL：传统布局只要字体、留白、状态和微动效统一，也能获得高完成度。

### 值得借鉴

- LifeOps 的功能详情应回到清晰 DOM 操作界面，但放在同一宇宙壳层内。
- 计划、记录和回顾可以像 BuouUI 的组件样例一样直接展示真实状态，而不是用解释性卡片代替产品。
- 使用一套强排版、少量边界和一个强调色，比大面积半透明玻璃更可信。
- 悬停与聚焦应改变清晰度、景深或照明，而不是统一放大。

### 不应照搬

- 它本质上是组件商城/文档产品，完整照搬会重新回到模板化 Bento 和卡片矩阵。
- 顶部促销条、Hot/Discount 标签、评分头像和大量营销入口与 LifeOps 无关。
- 其首页信息量很大，LifeOps 私人首页应更安静、更专注。

## 四、三站对比

| 维度 | Active Theory 当前版 | Active Theory V4 | BuouUI |
|---|---|---|---|
| 核心模式 | 沉浸式实时场景 | 电影片头式作品索引 | 产品/组件展示 |
| 第一焦点 | 悬浮媒体屏 | 巨型项目标题 | 产品主张 + 真实组件 |
| 背景角色 | 持续运行的世界 | 随项目变化的视频氛围 | 留白与结构网格 |
| 导航方式 | 场景物体 + 极简文字 | 标题序列 + 进度尺 | 标准吸顶导航 + 分类 |
| 内容详情 | 同一场景内展开 | 全屏覆盖式详情 | 标准 DOM 分区 |
| 运动来源 | WebGL、视频、粒子、视差 | 视频、排版切换、入场 | 滚动显现、悬停、局部模糊 |
| 主要优势 | 世界完整、记忆点极强 | 极简但有电影感 | 清晰、可复用、易操作 |
| 主要代价 | 性能、加载、可访问性 | 长入场、媒体预载 | 容易模板化、营销噪声 |

## 五、可以沉淀为 LifeOps 的设计原则

### 1. 一个持续世界，两种工作尺度

公开页和私人区不应是两套无关网页。公开页是远景，登录是穿越，私人首页是星系全景，功能详情是靠近某颗星球后的近景。背景、光源和空间坐标持续存在，内容只改变尺度和焦点。

### 2. 星球必须承担真实功能

每颗星球至少承担四种状态：远景识别、悬停预览、选中聚焦、详情锚点。离开详情后，它必须回到原轨道位置，不能销毁并重新生成。这样圆环才是信息架构，而不是装饰动画。

### 3. 体验层与操作层分开

- 体验层借鉴 Active Theory：场景、镜头、光照、空间转场。
- 操作层借鉴 BuouUI：清晰 DOM、真实内容、强排版、少量边界、明确反馈。
- 两层共享颜色、节奏和位置关系，但操作内容不能被塞进大玻璃卡片，也不能全部绘制到 Canvas。

### 4. 动效分三级

- 环境运动：极慢且持续，约 36–90 秒一个周期，不抢注意力。
- 导航运动：约 480–760ms，明确展示星球靠近、世界退后和内容展开。
- 操作反馈：约 120–240ms，用于保存、完成、撤回、输入校验和聚焦。

连续动画只能使用 transform、opacity、Canvas 或合成层；功能内容不得因场景动画阻塞输入。减少动态模式下保留空间关系，但停止持续漂移。

### 5. 昼夜不是换配色，而是换光照

白昼使用暖白空间、冷蓝局部光和低对比轨迹；夜晚使用深蓝黑天幕、月光边缘和稀疏星尘。布局、对象与功能位置不变，只改变光源、材质响应和环境运动速度。

### 6. 每屏只允许一个主要视觉事件

- 公开首屏：品牌主张与可探索星系，只能有一个主动作。
- 登录状态：圆环让位、登录界面出现，只展示身份动作。
- 私人首页：今日意图与星系导航，不同时展示五套摘要卡片。
- 功能详情：当前任务优先，星系退为导航锚点。

### 7. 建立渐进增强边界

- 高性能桌面：实时 Canvas 粒子、景深和指针视差。
- 普通设备：CSS 合成层与少量 Canvas。
- 低性能/减少动态：静态灯光、短淡入和完整键盘路径。
- 所有功能、文本和路由必须存在于语义 DOM；Canvas 只能表现世界，不能成为唯一操作入口。

## 六、下一轮不能继续做的事情

- 继续微调现有圆环大小、位置和渐变，却不重构“星系如何承载内容”。
- 给每个功能换一张玻璃卡片，形成另一套后台模板。
- 把 Active Theory 的噪点、视频或 WebGL 直接复制过来。
- 先写动画代码，再决定页面的镜头、层级和操作流程。
- 把“动得多”误认为“高级”，或为了丝滑隐藏真实加载与保存状态。

## 七、等待用户问题后的设计决策

本研究只形成参考规律，不替用户决定最终风格。收到用户对当前 LifeOps 的具体问题后，再进行以下工作：

1. 把每个问题归类为世界观、构图、排版、材质、动效、信息架构或操作反馈。
2. 判断哪些是局部问题，哪些要求替换整个视觉世界。
3. 提出 2–3 个完整方向，而不是零散修补方案。
4. 逐部分审核公开首屏、登录穿越、私人首页和功能详情。
5. 设计批准后再编写实施计划和代码。
